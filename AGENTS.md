# AGENTS.md — Actual Blocks

## Mission

Build a small, polished, standalone gallery of HTML/CSS blocks for consumers of Actual CSS. This is not a new CSS framework, not a component runtime and not a replacement for Actual CSS documentation.

## Source of truth

- Read `docs/brief.md`, `docs/architecture.md`, `docs/decisions.md`, `docs/blocks.md`, `docs/block-contract.md`, and `docs/acceptance.md` before changing structure.
- Consult the installed Actual CSS package (`node_modules/actual-css/`) and its documented components/layouts before choosing class names. Do not guess undocumented classes or npm exports.
- The project pins the published `actual-css` **0.16.1** release. Verify the installed version before assuming an API.
- `docs/roadmap.md` lists the release steps and the next blocks, in priority order.
- Use Actual CSS as a dependency, not a git submodule or copied source tree.

## Current state

- Twenty-four blocks are implemented. Marketing: Hero, Feature Grid, Bento Feature Grid, Testimonials, Pricing, Compare Plans, FAQ, Call to Action, Article with Contents. Application: Dashboard, Project Overview, AI Assistant, Sign-in, Settings, Plan Change, Checkout, Listing, Order Tracking, Code Verification, Empty State. Navigation: Site Header, App Topbar, App Sidebar, Site Footer.
- Catalog order lives in `src/blocks/order.json`.
- The static gallery, isolated iframe previews, desktop/mobile viewport control, light/dark preview themes, canonical source display, copy HTML/CSS, dependency notes and limitation notes are implemented.
- Blocks never contain a `<script>`. Drawers use native `command` / `commandfor`; the FAQ uses `<details name>`.
- Five blocks (article, project, signin, checkout, topbar) need Actual CSS's published enhancers. They declare `requiresJs: true` and `scripts` in metadata; only their previews load `dist/actual.full.js`. Do not write custom block JavaScript.
- Three blocks (hero, dashboard, signin) have a remix: an optional `remix.css` over the same HTML, made of one page-level brand theme rule (public Actual CSS tokens only) and rules scoped to the block, with pinned Fontsource fonts declared in `metadata.remix`. See `docs/block-contract.md` (Optional remix) and `docs/decisions.md` §13.
- The gallery is generated by `scripts/build.js`; `dist/` is not committed.
- `bun run build`, `bun run check`, `bun run contrast` (Actual CSS contrast checker on remix themes), `bun run test`, and the focused Playwright scripts are the supported commands.
- `docs/decisions.md` records the implemented architecture and the real limitations.

## Architectural rules

1. Keep this project independent from `actual-css`: it pins the published release, never a local checkout. Friction goes to the local, uncommitted `tmp/upstream-notes.md` as it is found; a fix may be made directly in the Actual CSS repository when warranted, following that repository's own `AGENTS.md`, as a separate change the maintainer reviews.
2. Preserve one canonical HTML source per block, reused for preview and copied output.
3. Keep block CSS explicitly scoped and exportable; never rely on hidden gallery rules.
4. Isolate preview rendering from the gallery (prefer simple generated iframe documents, validate the approach first).
5. Separate gallery-only controls, styles and JS from the exported block.
6. Prefer semantic HTML, native browser behaviors, public framework primitives and minimal JS.
7. Avoid a block DSL, complicated plugin architecture, framework-specific serialization or unnecessary libraries.
8. Make the project statically deployable, including from a repository subpath.
9. A block is a consumer-facing composition, not a tutorial for an individual component.

## Accessibility and behavior

- Proper landmarks/headings/labels; keyboard operation; visible focus; contrast; logical properties; responsive layout; reduced-motion when relevant.
- Ensure light/dark changes reach the actual block preview.
- Do not pretend a demonstration contains working auth, persistence or remote filtering. Implement local interactions or explicitly document what the application must supply.
- Every source snippet must work when used outside the gallery with its stated dependencies.

## Working method

1. Inspect the installed upstream API and current repository state.
2. Keep the canonical source, preview and copy path intact; do not hand-maintain duplicate snippets.
3. Work in small focused changes; no unrelated cleanup or speculative refactors.
4. Run focused checks first (`bun run check`, then the relevant Playwright spec); broaden to the full suite when scope justifies it. Do not continuously rerun the entire suite after tiny edits.
5. When a block changes visually, update the affected visual baseline deliberately and review the new image.
6. Review the full diff, dependencies, output size, source fidelity and test coverage before finishing.
7. Clearly report changes, why they were made, checks actually executed and remaining uncertainties.
8. Blocks are evergreen, with no compatibility guarantee. When a change adds or modifies blocks, list them in `CHANGELOG.md` under an unreleased heading; the maintainer picks the version (minor for new blocks, patch for improvements). Releases are a `package.json` bump plus a `vX.Y.Z` Git tag; nothing goes to npm, and GitHub Pages deploys the gallery from `master`.
9. Do not merge or publish the release yourself. Human retains the integration decision.

## Definition of done

Use `docs/acceptance.md`. Do not claim a release ready while any critical item remains unmet.
